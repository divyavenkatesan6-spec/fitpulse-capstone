# FitPulse: Gym Member Intelligence & Support Copilot

A capstone project on a **fictional gym chain** (1,000 members, 5 cities, January to June 2025).
All data is synthetic and generated by `generate_data.py`; no real personal data and no paid AI service is used.

**Business problem:** the gym loses members quietly. This project cleans the operational data, finds member groups,
predicts who is about to stop coming, handles support tickets safely, and answers policy questions.

## How to run
```bash
pip install -r requirements.txt
python generate_data.py      # creates data/raw and data/policies
python run_project.py        # runs every part in order
```
Then open `notebooks/FitPulse_Capstone.ipynb` and run all cells.

## Project structure
| Path | Purpose |
|---|---|
| `generate_data.py` | Creates messy fictional data (members, check-ins, payments, tickets, policies) |
| `src/data_pipeline.py` | Part A: audit, clean, validate, save to CSV and SQLite |
| `sql/queries.sql`, `run_sql.py` | Seven SQL queries (JOIN, CTE, window functions) |
| `src/member_models.py` | Part B: K-means segments and churn model |
| `src/triage.py` | Part C: privacy-first ticket triage |
| `src/policy_rag.py` | Part D: policy search with TF-IDF |
| `src/freeze_agent.py`, `run_agent_demo.py` | Part D: tool-using freeze agent |
| `outputs/` | Generated results, model and watchlist |

## Part A: Data cleaning
| Table | Raw rows | Clean rows | Main problems fixed |
|---|---|---|---|
| members | 1,000 | 1,000 | 20 city spellings, 9 gender spellings, 53 blank and 5 impossible ages |
| check-ins | 55,988 | 48,530 | 120 duplicates, 374 negative durations, 3,661 bad calories, 7,355 check-ins before the join date |
| payments | 6,040 | 6,000 | 40 duplicates, 15 unreadable amounts |

Each rule is a commented block in `clean_data()`. `validate()` uses assertions that stop the pipeline if bad data remains.

## Part B: Segments and churn
- **Segments (K-means, K=4, best silhouette 0.467):** Champions (265 members, about 99 visits), Regulars (387), At Risk (197) and Fading (146). The last two have not visited for about 45 days.
- **Churn model:** features come only from before 1 June; the label is "no visit in June". About 33% of members churn, so a model that always predicts "stays" already gets 66.8% accuracy, which is why F1 is used.
  Random forest: precision 0.887, recall 0.955, F1 0.920. Logistic regression: F1 0.905.
- **Watchlist:** the saved model scores all members at 1 July and writes `outputs/retention_watchlist.csv`.
- **Caveat:** the score is high because synthetic leavers fade out clearly. Real data would score lower.

## Part C: Ticket triage
Empty and over-long tickets are blocked. Emails, phone numbers and member IDs are redacted before the model sees the text
(82 emails, 66 phones, 64 member IDs removed). The simulated model fails sometimes, so the code retries with growing waits and validates every answer.
Result on 168 tickets: 136 classified from JSON, 14 recovered by keyword fallback, 10 invalid answers and 8 blocked tickets sent to human review.
Harassment goes to the regional manager as HIGH priority (the policy says 4 hours); Premium members get HIGH priority.
Accuracy on classified tickets is 100% because the simulated classifier is keyword-based; the value of this part is the safety code.

## Part D: Policy search and freeze agent
- **Search:** documents are chunked (40 words, 10 overlap) and ranked by TF-IDF cosine similarity. 12/12 questions found the right document and fact; 2/2 unanswerable questions were refused.
- **Agent:** tools `get_member`, `search_policy`, `check_freeze`, `approve_freeze`. Rules: 15 to 60 days, request 3+ days before billing, fee INR 200, one free freeze per year for Premium.
  It stops after 5 steps and hands over to a human (as the conduct policy requires), with token and time limits and a checkpoint after every step.
  Nine test scenarios behave as expected (approvals, three kinds of rejection, unknown member, missing info, loop handover).

## Limitations
- Data and the "AI model" are simulated; real results would be less clean.
- The freeze ledger is a local file, not a real billing system.
- A real system needs access control, monitoring, model drift checks and human approval workflows.

## What I learned
Before this project I did not realise how much of data work is cleaning. About 7,000 check-ins had to be removed because they were dated before the member joined, and the audit step is what found them. I also learned that accuracy can be misleading: about 33% of members churn, so a model that always predicts "stays" already scores 66.8%, which is why I used F1 to compare models. In the ticket triage part I learned to hide personal details before the AI sees any text and to send unclear answers to a human instead of guessing. The most interesting part was the freeze agent, because it follows the policy rules, stops after 5 steps and hands over to a human. With more time I would use real data and a real language model, because my simulated model made the results look better than real life would.
